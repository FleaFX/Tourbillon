Chapter 3

State and snapshots

In the end, what counts is what the application builds from the log. Raft calls that the state machine: every machine applies the same entries in the same order and so reaches the same state. Here I draw the line between Tourbillon and the application: how the entries reach the application, who keeps the state, and who decides when the start of the log may go.

Applying the entries

Tourbillon hands the application every committed entry through the feed: a sequence in the order of the log, without skipping one. The application applies each entry to its state, MSSP for example by adding the event in it to its storage. What the application does with an entry, Tourbillon never sees.

We also write a few entries of our own: the empty entry of a new leader (chapter 4) and the entries that change the replicas of a group (chapter 5). The feed hands those too, marked as Tourbillon's, and the application skips them or reads them. I chose that over a feed with only the application's entries, because then every index in the feed follows the one before it, and the point the application has applied up to is simply the last index it saw.

Committing and applying are two different moments. An entry is committed once it is safe (chapter 2); the application applies it a little later, at its own pace. We do not wait for the application before we answer "committed", so a slow application should not make proposing slower. I measured it: in a group of three with 100 proposers, a feed reader that slept 10 ms after every batch left the group at 9,154 committed proposals per second, against 9,429 without the pause, within the noise of the measurement.

"Committed" therefore only means that the entry is safely in the log, not that the application has done what the entry asks. Usually the difference does not matter, but sometimes it does. An example with MSSP:

  1. A service asks MSSP: "add this event to stream order-42, which should be at version 7". At the same moment, a second service asks the same, with another event.
  2. MSSP proposes both as entries. Tourbillon commits them one after the other: the first at index 501, the second at index 502. Both are now safely in the log.
  3. MSSP applies entry 501: the stream is at version 7, so the event is added, and the stream goes to version 8. Then it applies entry 502: the stream is no longer at version 7, so that event is refused.
  4. Only now does MSSP know what to answer each service: "added" to the first, "conflict" to the second.

MSSP answers its service once it has applied the entry, not at "committed". Tourbillon helps by giving the index of every committed entry, so MSSP knows to wait until it has applied index 502 before it answers the second service. It cannot check the version before it proposes, because two services can propose at the same moment and only the order in the log decides which one was first. Entry 502 stays in the log, although it changed nothing: Tourbillon never takes a committed entry back, and what such an entry means is up to the application.

The application keeps its own state

The state belongs to the application, in a form it chooses itself, and Tourbillon never touches it. Together with its state, the application stores up to which index it has applied the log, in the same step, so that after a crash the two always match.

It does not have to store its state after every entry. When the application starts again, it tells Tourbillon up to which index its state on disk goes, and the feed hands it every committed entry after that index again, in order. So an application may keep its state in memory for a while and write it to disk now and then; what was not on disk yet simply comes again from the log.

Letting go of the start of the log

A log cannot grow forever. Now and then the application tells Tourbillon up to which index it no longer needs the log: it lets go up to that point, and Tourbillon removes the segments that lie completely before it (chapter 2). Raft calls this log compaction.

The entries before that point are then gone, but another machine may still need what they held: a new replica, or a replica that fell far behind (chapter 4). It cannot get those entries any more, so it gets the state instead. That is why the application may only let go up to a point where it can give its state as it was at that point: a snapshot. A machine that starts from the snapshot and then applies every entry after it ends up with the same state as all the others.

The application keeps its snapshots itself, in its own form. Tourbillon only asks for one when another machine needs it, and hands a received snapshot to the application on that machine to start from. Chapter 5 says how a snapshot travels.

Some Raft libraries decide themselves when to take a snapshot, and the application only serialises its state. I cannot let Tourbillon decide that, because it never reads the entries and so cannot know when a part of the log is no longer needed.

How MSSP and Remontoire use this

The two applications let go for different reasons, and their snapshots look very different; I treat them the same way. MSSP keeps every event forever, in its own files. Once a part of the log is safely in those files, MSSP no longer needs it and lets go, and its snapshot is those files: large, because they hold every event.

Remontoire keeps its messages in the log itself and reads them from there, so it lets go only once the retention of the stream allows it. Its snapshot is small: the cursors of the groups and the copies of parked messages, as they were at that point. The messages after it are still in the log.

What must always be true
  • The application gets every committed entry, in the order of the log, without gaps, and never an entry that was not committed.
  • After a restart, Tourbillon hands again every committed entry after the index up to where the application's state is on disk.
  • The application lets go only up to a point where it can give a snapshot; Tourbillon removes only what lies before that point.
  • A machine that starts from a snapshot and then applies every entry after it, ends up with the same state as every other machine.
  • Committing never waits for the application to apply.
