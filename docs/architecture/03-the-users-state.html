Chapter 3

The user's state

In three sentences

Tourbillon hands the accepted entries to the user in the order of the log, and the user applies them to its own state, at its own pace. The user keeps its state itself, and after a restart Tourbillon hands it again every entry after the point up to where that state was on disk. The user also decides up to where the start of the log may go, but only up to a point where it can give its state as a snapshot, so that another machine can start from it.

Applying the entries

Tourbillon hands the user every accepted entry, one after the other, in the order of the log, without skipping one. The user applies each entry to its state: MSSP adds an event to its storage, Remontoire moves the cursor of a group forward. Tourbillon never looks at what the user does with it.

Accepting and applying are two different moments. An entry is accepted once it is safe (chapter 2); the user applies it a little later, at its own pace. Tourbillon does not wait for the user before it answers "accepted", and a slow user never makes proposing slower.

"Accepted" therefore only means: the entry is safely in the log. It does not mean that the user has already done what the entry asks. Usually that difference does not matter, but sometimes it does. An example with MSSP:

  1. A service asks MSSP: "add this event to stream order-42, which should be at version 7". At the same moment, a second service asks the same, with another event.
  2. MSSP proposes both as entries. Tourbillon accepts them, one after the other: the first at index 501, the second at index 502. Both are now safely in the log.
  3. MSSP applies entry 501: the stream is at version 7, so the event is added, and the stream goes to version 8. Then it applies entry 502: the stream is no longer at version 7, so that event is refused.
  4. Only now does MSSP know what to answer each service: "added" to the first, "conflict" to the second.

So MSSP does not answer its service at "accepted", but only once it has applied that entry. Tourbillon helps with that by giving the index of every accepted entry: MSSP waits until it has applied index 502 before it answers the second service. Why MSSP cannot check the version before it proposes: two services can propose at the same moment, and only the order in the log decides which one was first.

The user keeps its own state

The state belongs to the user, in its own form: MSSP keeps its own files on disk, Remontoire keeps cursors and parked messages. Together with its state, the user stores up to which index it has applied the log. Both are written together, in one step, so that after a crash they always match.

The user does not have to store its state after every entry. When it starts again, it tells Tourbillon up to which index its state on disk goes, and Tourbillon hands it every accepted entry after that index again, in order. So a user may keep its state in memory for a while and write it to disk now and then: what was not on disk yet simply comes again from the log.

Letting go of the start of the log

A log cannot grow forever. So the user tells Tourbillon, now and then, up to which index it no longer needs the log: it lets go up to that point, and Tourbillon removes the segments that lie completely before it (chapter 2).

But the entries before that point are gone, and another machine may still need what they contained: a new copy, or a copy that fell far behind (chapter 4). It cannot get those entries any more, so it gets the state instead. That is why the user may only let go up to a point where it can give its state as it was at that point: a snapshot. A machine that starts from the snapshot, and then gets every entry after it, ends up with the same state as all the others.

The user keeps its snapshots itself, in its own form. Tourbillon only asks for one when another machine needs it, and hands a received snapshot to the user to start from. How a snapshot goes from one machine to another is in chapter 5.

How MSSP and Remontoire use this

The two users let go for different reasons, and their snapshots look very different. Tourbillon treats them the same way.

  • MSSP keeps every event forever, in its own files. Once a part of the log is safely in those files, MSSP no longer needs it and lets go. Its snapshot is those files: large, because they hold all events.
  • Remontoire keeps its messages in the log itself: it reads them from there. So it lets go only once the retention of the stream allows it. Its snapshot is small: only the cursors of the groups and the copies of parked messages, as they were at that point. The messages after it are still in the log.

For both, Tourbillon only promises what chapter 2 says: it removes whole segments, and only before the point the user let go of. When to let go stays the user's decision.

What must always be true
  • The user gets every accepted entry, in the order of the log, without gaps, and never an entry that was not accepted.
  • After a restart, Tourbillon hands again every accepted entry after the index up to where the user's state is on disk.
  • The user lets go only up to a point where it can give a snapshot; Tourbillon removes only what lies before that point.
  • A machine that starts from a snapshot and then applies every entry after it, ends up with the same state as every other machine.
  • Accepting never waits for the user to apply.

What Tourbillon does not do here

  • Tourbillon does not keep, read or check the user's state; it only knows the indexes the user tells it.
  • Tourbillon never takes an accepted entry back. An entry that turns out to be wrong when the user applies it, stays in the log; what it means is up to the user.
  • Tourbillon does not decide when to let go, and has no retention rules of its own.

Words used in this chapter

Apply
What the user does with an accepted entry: change its state according to it.
Let go
Tell Tourbillon that the log is no longer needed up to an index, so that the segments before it may be removed.
Snapshot
The user's state as it was at one index, in the user's own form, so that another machine can start from it.
