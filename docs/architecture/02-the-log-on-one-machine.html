Chapter 2

The log on one machine

Before there is any Raft, there is a log on one disk, and a lot can already go wrong there, such as a power failure halfway through a write or a disk that fills up. An application that runs Tourbillon on a single machine has only this log, and every replica in chapter 4 keeps its log in the same way.

A log is a row of segments

Every log has its own folder on disk, and in it the log is cut into segments: files that each hold the entries of one stretch of indexes. New entries go at the end of the last segment. When that one reaches the segment size, a setting of the log, the next entry starts a new file.

Segments make removing cheap. Once the application no longer needs the start of the log (chapter 3 says how it decides that), Tourbillon deletes the segments that lie completely before that point. It never cuts a segment in two: a segment that still holds one entry the application needs, stays whole.

An entry can therefore stay a little longer than the application needs it, never shorter. Too long costs some disk space; too short would lose something that was promised. A smaller segment size keeps entries less long past that point, at the cost of more files.

When an entry counts as committed

An operating system does not write to disk straight away. It keeps new data in memory and writes it later, and if the power fails in between, that data is gone. So after writing, we call fsync, which asks the disk to really store what was written and returns only once it has. Only then does it answer "committed".

Some systems offer to answer earlier, from memory, as a faster option. I left that out on purpose. An application that asks for "committed" asks for exactly this promise, and I am afraid that an option that quietly weakens it would sooner or later cause a loss that nobody can explain.

An fsync is slow compared to everything else, so I do not write entries one by one. Everything that was proposed while the disk was busy goes into the next write, together, and one fsync answers all of it. This is called group commit. When it is quiet an entry is written on its own straight away; when it is busy many share one write.

How much that matters shows in a measurement on a laptop (Intel Core i7, Windows 11) with a client NVMe SSD without power-loss protection. One log there does about 820 fsyncs per second, 1.1 ms each at the median. Entries of 256 bytes written one per fsync give about 820 entries per second. In batches of 1000, a write takes 2.6 ms at the median, and the same log takes 352,000 entries per second. A server SSD with power-loss protection can confirm an fsync from its own protected cache, so I expect an fsync to cost much less there, but I have not measured it.

A common alternative is to wait a moment before each write, to gather more entries. I chose not to: the numbers above suggest that batching already grows with the load on its own, and a wait would cost every entry latency when it is quiet, with one more setting to tune.

A write can fail, for example because the disk reports an error. Then every entry of that write gets an error, and we cut the file back to where it was before the write, so that a later write cannot make a part of it count after all. If even that fails, or a new segment cannot be started cleanly, the log stops taking entries and reports that it is broken, rather than go on with a log it can no longer trust.

After a crash

Every entry on disk carries its index and a checksum (CRC32C) computed from its content. When Tourbillon starts again, it reads the end of every log and checks it. An entry that was only half written when the machine stopped, a torn write, has a wrong checksum or simply stops too early. Tourbillon cuts it off, with everything after it. That entry was never committed, because its fsync had not returned, so the application never got "committed" for it.

The entries of one write may reach the disk in any order, so after a crash a whole entry can stand behind a half-written one. Both belong to the write that never finished, and both go. But a bad entry can also be real damage: a disk that changed bytes it had already stored. To tell the two apart, I mark the first entry of every write, and start a write only once the one before it is on disk. A bad entry with the start of a later write behind it was therefore already on disk, and is damage. An example:

  1. Entries 1 to 10 are written together, then entries 11 to 20. The machine stops while it writes entries 21 to 30.
  2. After the restart, entry 25 has a wrong checksum, and no write starts after it. Entry 25 belongs to the last write, which never finished: Tourbillon cuts off entries 25 to 30.
  3. Had entry 15 been the bad one, Tourbillon would find the start of the write of entry 21 behind it. Entries 11 to 20 were then already on disk, so entry 15 is damage, and the log is refused.

One case cannot be told apart: damage in the write just before the last one, when the first entry of the last write is itself half written. In the example, entry 15 is damaged and entry 21 is torn. Nothing marks a later write any more, so Tourbillon cuts off from entry 15, as if it were a torn end.

I looked at two other ways and chose neither. Cutting off from the first bad entry, always, is the simplest, but it would also cut real damage silently, and on a group a replica that counted for a majority could lose committed entries without a sign. A "write done" mark after every write would be exact, but it needs a second fsync per write, which I expect would cost about half the speed on the path every entry takes. The mark costs one bit per entry and a search only when starting after a crash; the one case it cannot tell apart is the price.

A wrong checksum in a segment before the last one is always damage, since that segment was complete and has changed. Tourbillon then refuses to open the log, with a clear error, instead of skipping the damaged entries: skipping would leave a hole in the indexes and hand the application a log that is not the one it was promised. On one machine the log then has to be restored; in a group, the replica can be made again from the others (chapter 5).

Next to the log, we keep a few small facts, such as up to where the start of the log was removed (chapter 3) and the term and vote of chapter 4. Each is written to a new file first, stored with fsync, and only then put in the place of the old one. After a crash each is either the old version or the new one, never half of each.

When the disk is full

Storage is full when the disk is full, or earlier, when the logs of one Tourbillon instance reach a maximum size that was set for them. The maximum is optional, and the free disk space always counts as well, so a disk that fills up for other reasons gives the same clear refusal instead of a failed write.

When storage is full, Tourbillon refuses new entries and touches nothing that was committed. Removing segments goes on, so the space comes back once the application lets go of the start of a log. Tourbillon never makes room by removing entries the application still needs.

But sometimes an application must write in order to free space. In Remontoire a message may only go once every reader has acknowledged it, and an acknowledgement is itself an entry. So I keep some space in reserve, and with every proposal the application says whether that entry may use it. Remontoire allows it for acknowledgements, which help free space, and not for new messages. Once the reserve is used up too, every entry is refused.

What must always be true
  • An entry Tourbillon called committed is on disk: a crash or a power failure right after does not lose it.
  • An entry is in the log completely, or not at all.
  • The indexes of a log have no holes: from the first entry still kept to the last, every number is there.
  • A failed write leaves nothing behind that could later count as committed.
  • Tourbillon only removes whole segments, and only segments that lie completely before the point the application let go of.
  • When storage is full, only new entries are refused; nothing committed is removed to make room.

What Tourbillon does not do here

On one machine, Tourbillon does not protect against losing the disk itself; that is what more machines are for (chapter 4). And it does not compress or encrypt entries. An application that wants its entries smaller or secret does that before proposing them; encrypting the whole disk is up to the host.
