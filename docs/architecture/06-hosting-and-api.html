Chapter 6

Hosting and API

In three sentences

Tourbillon runs inside its user, which runs inside an application of yours, the host: one Tourbillon instance can carry many groups, and several instances can run side by side in one process. Tourbillon never opens a network port: the host puts its endpoints in its own web application and makes sure only its own machines can reach them. The user has one small API to run its groups, every setting has a default, and a test package lets users try their own state against crashes and a broken network.

Where Tourbillon runs

Tourbillon is a library inside its user. Remontoire and MSSP build it in; an application, the host, builds in Remontoire or MSSP. So Tourbillon always runs in the process of the host, on every machine the host runs on.

One Tourbillon instance carries all the groups of one user on that machine, each in its own folder under one data folder. Remontoire may have hundreds of groups, one per partition; MSSP has one. Messages of many groups that go to the same machine travel together, so many groups do not mean many separate conversations.

Several instances can run side by side in one process, for example a Remontoire and an MSSP in the same service, or one Remontoire per customer. They share nothing: each has its own data folder, settings and measurements. Tourbillon keeps no state that is shared by the whole process.

The network goes through the host

The copies of a group talk to each other over the network. Tourbillon does not open a port for that. It supplies endpoints, and the host puts them in its own web application, next to its other endpoints. The host chooses the port and protects the traffic.

Tourbillon trusts every copy of a group (chapter 1), so protecting this traffic is not optional. At the least, the host makes sure that:

  • only its own machines can reach the endpoints, for example because every machine has a certificate and both sides check each other's (mutual TLS);
  • it tells Tourbillon which machine a connection comes from, for example the name in its certificate.

A message between copies does not say who sent it: Tourbillon only knows that from what the host says about the connection. So one machine cannot speak in the name of another. Tourbillon refuses a message about a group that the sending machine has no copy of. That mostly catches mistakes rather than attacks: two machines set up with the same name, a test machine that reaches production, a removed machine that keeps running.

The API

The user works with its groups through one small API. Per group, it can:

  • Start a group on this machine, with its copies, or open it again after a restart, saying up to which index its own state is on disk (chapter 3).
  • Propose entries. The answer is always accepted with the index, refused with a reason, or unknown (chapter 4). With every proposal, the user says whether the entry may use the reserve (chapter 2).
  • Read the accepted entries: an endless sequence, in the order of the log, that first catches up and then follows new entries as they are accepted.
  • Let go of the start of the log up to an index, and give or take in a snapshot when Tourbillon asks for it (chapter 3).
  • Add or remove a copy, and hand over leadership (chapter 5).
  • Look: which copy leads, the term, and how far every copy is.
  • Remove its copy from this machine, which deletes its folder.

The accepted entries are lent, not given. Tourbillon reads them from disk into a piece of memory, and hands the user a batch that points into it. When the user asks for the next batch, Tourbillon uses the same memory again for the next entries. An example:

  1. Remontoire gets a batch with entries 501 to 600. Entry 550 is an acknowledgement: Remontoire reads the position from it and moves the cursor of the group. It needs nothing more from the entry, so it copies nothing.
  2. Entry 560 is a message that must be parked. Remontoire has to keep it anyway, so it copies that one entry into its own storage.
  3. Remontoire asks for the next batch, entries 601 to 700. They take the place of 501 to 600 in the same memory.

So the rule for the user: what you still need after a batch, you copy yourself. Giving every entry its own memory instead would be simpler, but at a hundred thousand entries per second that means a hundred thousand pieces of memory per second for .NET to clean up, mostly for entries nobody keeps. A user that forgets to copy would see wrong bytes later, without any error. That is why the test package fills the memory with rubbish after every batch: such a mistake then shows up at once in the user's own tests, not one day in production.

Watching Tourbillon

Tourbillon gives measurements and traces through the standard .NET mechanisms, which OpenTelemetry understands, and writes its logs through the logging of the host. Each instance has its own measurements. Examples: how long a write to disk takes, entries accepted per second, storage used, elections; and per group: which copy leads, and how far behind every copy is. Tourbillon also offers health checks the host can register, such as a log that reported itself broken (chapter 2), or a group that has had no leader for too long. Which dashboard or tool shows this is the host's choice.

The test package

Most mistakes in this kind of software show only under bad luck: a crash at the wrong moment, a message that arrives late or twice. So Tourbillon comes with a test package that makes bad luck on purpose. It runs a group of several copies in one test, with a fake network and a fake clock, and brings in faults: messages lost, late or out of order, machines that crash and lose what was not on disk yet, a network split in two. After every step, it checks that the rules of chapter 4 still hold.

Users test with it too: Remontoire and MSSP run their own state on top of it, and check their own rules under the same bad luck. Every run is driven by one number, so a run that fails can be repeated exactly.

What must always be true
  • Tourbillon never opens a network port by itself.
  • Instances in one process share nothing.
  • Tourbillon knows who sent a message only from what the host says about the connection, and refuses a message about a group the sending machine has no copy of.
  • A proposal always ends accepted, refused or unknown.
  • Every setting has a default.

What Tourbillon does not do here

  • Tourbillon does not choose certificates, ports or how the traffic is protected; the host does.
  • Tourbillon does not decide who may use the user's own API; that is the user's and the host's business.
  • Tourbillon does not choose a dashboard, an exporter or a log tool.
