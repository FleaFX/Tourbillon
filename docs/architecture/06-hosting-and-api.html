Chapter 6

Hosting and API

The earlier chapters describe one group. In practice Tourbillon runs inside an application, next to other code, with many groups at once. Here I describe how it fits in there, the API the application works with, and the test package.

Where Tourbillon runs

Tourbillon is a library inside the application, and the application runs in a host. By host I mean the process that a team deploys on its machines, and it has a web server of its own. Remontoire and MSSP are libraries too, so with them there are three layers: a service builds in Remontoire, and Remontoire builds in Tourbillon. An application that uses Tourbillon directly is its own host. In both cases, Tourbillon runs in the host's process, on every machine the host runs on.

One Tourbillon instance carries all the groups of one application on that machine, each in its own folder under one data folder. Remontoire may have hundreds of groups, one per partition; MSSP has one. The messages of many groups that go to the same machine travel together, so many groups do not mean many separate conversations.

Several instances can run side by side in one process, for example a Remontoire and an MSSP in the same service, or one Remontoire per customer. They share nothing: each has its own data folder, settings and measurements, and Tourbillon keeps no state that is shared by the whole process.

The network goes through the host

The replicas of a group talk to each other over the network, but we open no port for that. Tourbillon supplies endpoints, and the host puts them in its own web server next to its other endpoints. The host chooses the port and protects the traffic.

I could have let Tourbillon open a port of its own. But the host already has a web server that its team knows how to secure and watch, and a second server in the same process would need all of that a second time. With endpoints, the replicas talk over the port the host already has. The core of Tourbillon knows the network only through an interface, and gRPC is in a package of its own. I do not want to force gRPC on anyone; for now it is the only transport, but another one can be added without touching the core.

Tourbillon trusts every replica of a group (chapter 1), so the host has to protect this traffic. At the least, the host makes sure that only its own machines can reach the endpoints, for example because every machine has a certificate and both sides check each other's (mutual TLS), and it tells Tourbillon which machine a connection comes from, for example the name in its certificate.

A message between replicas does not say who sent it; Tourbillon only knows that from what the host says about the connection, so one machine cannot speak in the name of another. Tourbillon refuses a message about a group that the sending machine has no replica of. That mostly catches mistakes rather than attacks: two machines set up with the same name, a test machine that reaches production, a removed machine that keeps running.

The API

The application works with its groups through one small API. Per group, it can:

  • start the group on this machine with its replicas, or open it again after a restart, saying up to which index its own state is on disk (chapter 3);
  • propose entries, each with whether it may use the reserve (chapter 2); the answer is always committed with the index, refused with a reason, or unknown (chapter 4);
  • read the committed entries through the feed, an endless sequence in the order of the log that first catches up and then follows new entries as they are committed;
  • let go of the start of the log up to an index, and give or take in a snapshot when Tourbillon asks for it (chapter 3);
  • add or remove a replica, and transfer leadership (chapter 5);
  • look: which replica leads, the term, and how far every replica is;
  • remove its replica from this machine, which deletes its folder.

Who may call this API is not Tourbillon's business; that is up to the application and the host.

Reading committed entries

The application does not get its own copy of the committed entries. We read them from disk into a piece of memory and hand the application a batch that points into it. When the application asks for the next batch, we use the same memory again for the next entries. An example:

  1. Remontoire gets a batch with entries 501 to 600. Entry 550 is an acknowledgement: Remontoire reads the position from it and moves the cursor of the group. It needs nothing more from the entry, so it copies nothing.
  2. Entry 560 is a message that must be parked. Remontoire has to keep it anyway, so it copies that one entry into its own storage.
  3. Remontoire asks for the next batch, entries 601 to 700. They take the place of 501 to 600 in the same memory.

The rule for the application is therefore: what you still need after a batch, you copy yourself.

Giving every entry its own memory would be simpler. But allocations have to stay low in Tourbillon, so lending was the obvious choice for me. One log on the laptop of chapter 2 can write 352,000 entries per second, and the feed has to keep up with that; with its own memory per entry, that would be as many pieces of memory per second for .NET to clean up, mostly for entries nobody keeps. The price of lending is a mistake that does not show: an application that forgets to copy sees wrong bytes later, without any error. That is why the test package fills the memory with rubbish after every batch, so that such a mistake is much more likely to show up in the application's own tests than in production.

Watching Tourbillon

Tourbillon gives measurements and traces through the standard .NET mechanisms, which OpenTelemetry understands, and writes its logs through the logging of the host. Each instance has its own measurements: how long an fsync takes, entries committed per second, storage used, elections, and per group which replica leads and how far behind every replica is. Tourbillon also offers health checks the host can register, such as a log that reported itself broken (chapter 2), or a group that has had no leader for too long. Which dashboard or tool shows all this is the host's choice.

The test package

Many mistakes in this kind of software show only under bad luck: a crash at the wrong moment, a message that arrives late or twice. So I wrote a test package that makes bad luck on purpose. It runs a group of several replicas in one test, with a simulated network, disk and clock, and brings in faults: messages lost, late or out of order, machines that crash and lose what was not on disk yet, a network split in two. After every step it checks the five safety properties of the Raft paper and the promises of chapter 4.

Every run is driven by one number, the seed, so a run that fails can be repeated exactly. Tourbillon's own tests run 100 seeds on the simulated disk with every change. Applications test with the same package: Remontoire and MSSP run their own state on top of it, and check their own rules under the same bad luck.

What must always be true
  • Tourbillon never opens a network port by itself.
  • Instances in one process share nothing.
  • Tourbillon knows who sent a message only from what the host says about the connection, and refuses a message about a group the sending machine has no replica of.
  • A proposal always ends committed, refused or unknown.
  • Every setting has a default.
